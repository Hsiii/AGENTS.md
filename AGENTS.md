Always commit your changes with Conventional Commits. Only use `style` for formatting-only changes, not CSS changes. Prefer patch staging if there are unrelated user edits.
Preserve meaningful project history. Commits should record the path of implementation through coherent milestones, not every tiny edit, typo, experiment, or failed attempt. The goal is neither to keep every small change nor to collapse a whole pull request into one commit merely because its changes are related.
Commit each completed prompted task or supplied browser annotation batch before yielding, grouping meaningful chunks without splitting every small annotation. Work in implement -> commit cycles so distinct milestones remain visible, while folding trivial corrections and trial-and-error within the task into the commit they complete.
Amend only when explicitly requested or when the current follow-up is a trivial correction to the immediately preceding, unshared, agent-authored commit. Otherwise, create a new Conventional Commit. Do not squash distinct prompts or milestones merely because they contribute to the same pull request.
Never rewrite pushed/shared history, user-authored commits, or unrelated commits without explicit permission. Only rewrite local agent-authored commits within the last 3 commits, and only when doing so preserves meaningful milestones. If the matching commit is older, later work depends on it, or the rebase would cross unrelated work, make a new Conventional Commit instead.
For suitable projects, use `bun`, use `bunx` when the tools you need are not installed.
When changing CSS, use tokens instead of hardcoded values, keep sizes and spacing in multiples of 4, and check whether the rule is overridden or overrides anything unintended.
Assume dev is running on localhost, only spin one up if not. Leave in-app browser intact for further annotation.
